## 1. Blockers — must happen before this is live

Nothing works in production until both of these are done. Right now a real
submission would return `503 Email is not configured yet`.

### 1a. Add the Resend key to Vercel

The key currently exists **only** in `.env.local`, which is gitignored and never
deploys. Local working ≠ production working.

- Vercel → project `drksub` → Settings → Environment Variables
- Add `RESEND_API_KEY` = the `re_...` value from `.env.local`
- Apply to Production (and Preview if you want PR deploys to work)
- Redeploy — env var changes do not take effect on the existing deployment

Takes about 30 seconds. Do this one first.

### 1b. Verify drkgroup.xyz in Resend

The Resend account has **no verified domains**, so sending as
`contact@drkgroup.xyz` fails. This is the slow one — start it early, DNS takes
time to propagate.

- resend.com/domains → Add Domain → `drkgroup.xyz`
- Add the DKIM + SPF records it gives you at your registrar
- **Leave the existing MX records alone.** Domain verification is for *sending*
  only and does not reroute your incoming mail. Nick's mailbox keeps working.
- Wait for it to flip to Verified

Use a **Sending-access** key restricted to the domain, not a Full-access key. If
the key in `.env.local` is Full-access, make a new restricted one and swap it.

Until this is verified, Resend only accepts `onboarding@resend.dev` as the sender
and only delivers to the account owner (`noiseg12322@outlook.com`). That is how
the flow was tested.

## 4. Turn on Telegram (optional, 2 minutes)

Currently both vars are empty, so the Telegram card does not render at all and
the confirmation just shows the redirect. Nothing is broken — it is off.

1. Create one private DRK group
2. Add yourself, Goku (`@gokusan0x`) and the bot `@darrrrkkkkbot`
3. Group → Manage → Invite Links → create a permanent link
4. Set `TELEGRAM_INVITE_LINK` in Vercel to that link

That alone makes the "Open Telegram" card appear on the confirmation screen and
in the receipt email.

For the bot to also post each submission into that group:

5. Post any message in the group, then open
   `https://api.telegram.org/bot<TOKEN>/getUpdates`
6. Read `result[].message.chat.id` (supergroups look like `-1001234567890`)
7. Set `TELEGRAM_CHAT_ID` in Vercel

The token is already in `.env.local` as `BOT_FATHER` — the code accepts that name
as an alias for `TELEGRAM_BOT_TOKEN`.

## 5. After a few real submissions

- **Narrow `SUBMISSIONS_TO`.** It currently defaults to `contact@,nick@` because
  verifying a domain for sending does *not* create an inbox at `contact@`. Keep
  both until you have watched several real submissions land, then decide. This is
  cleanup, not launch work.
- **Watch the rate limiter.** It is an in-memory `Map`, so it is per warm
  serverless instance rather than global. It stops a rapid loop from one source;
  it does not stop a distributed or slow-drip one. If spam actually shows up,
  swap `rateLimit()` in `api/submit.js` for Upstash Redis — it is self-contained
  and nothing else changes. Vercel's WAF is the other option and needs no code.
- **Consider a real inbox for `contact@`** if you want people to be able to write
  to the address on the form.

## Decision record — why there is no auto-created group

Investigated 27 Sep 2026. Rejected deliberately; do not let someone "fix" this later
without reading this section.

**The Bot API cannot create groups.** There is no such method. Not an oversight.

**MTProto (Telethon/GramJS with a real user account) can, but should not be used here:**

1. **Auto-adding the applicant mostly fails anyway.** `messages.createChat` returns
   a `missing_invitees` list and `channels.inviteToChannel` documents
   `USER_PRIVACY_RESTRICTED` and `USER_NOT_MUTUAL_CONTACT`. Telegram's protocol is
   built around the assumption you will often be unable to add someone and must
   fall back to an invite link — which is what the form already does. Crypto
   founders lock this setting down specifically because of this kind of automation.
2. **We cannot verify Telegram identity.** The form field is free text labelled
   "Telegram or X". `@oxnik` may be an X handle. Resolving it against Telegram
   could invite an unrelated real person into a group named "DRK × <Project>",
   leaking that a named project is talking to DRK.
3. **Ban risk lands on a real person's account.** Telegram's terms: flooding or
   spamming via the API and "you will be banned forever"; unofficial-client
   accounts are "automatically placed under observation". `messages.createChat`
   returns `USER_RESTRICTED` — *"you're spamreported, you can't create channels
   or chats."* One irritated applicant reporting the account ends group creation.
4. **A session string is a full account takeover artifact.** It bypasses 2FA
   entirely and reads every DM that account can see. Worse to store than a password.
5. **Serverless cannot hold an MTProto session.** It is a stateful persistent TCP
   connection; concurrent invocations conflict and re-authing per request is
   exactly the pattern Telegram flags. It would need a separate always-on worker,
   a queue and a datastore.

**The safe alternative if this is ever wanted:** the `startgroup` deep link —
`t.me/darrrrkkkkbot?startgroup=<token>`. The applicant taps it, Telegram asks
*them* to create a group and add the bot; the bot then matches the token to the
submission, titles the room, posts the context and generates invite links for DRK
via `createChatInviteLink`. Same outcome, but the applicant creates the group, so
there is no userbot, no session string, no ban risk and no privacy failure. Costs
one extra tap and needs a bot webhook plus a KV store (Vercel KV or Upstash —
neither is provisioned yet).

Worth noting the original spec said "per **approved** submission", but there is no
approval step in the system — every submission just emails. Approval is a human
moment anyway, and making the room by hand at that point is ~15 seconds.

## Reference

**Integration points** — if Telegram behaviour changes, these are the only two places:
- `notifyTelegram()` in `api/submit.js` — everything server-side
- `finish()` in `app.js` — where the invite link reaches the UI

**Env vars** — full list with defaults and comments is in `.env.example`.
Only `RESEND_API_KEY` is required. Aliases accepted: `RESEND_API`, `BOT_FATHER`.

**Run locally:**
```bash
vercel dev            # reads .env.local
```

**Check what Resend actually sent:**
```bash
curl -s -H "Authorization: Bearer $RESEND_API_KEY" \
  "https://api.resend.com/emails?limit=10"
```
Look at `last_event` — `delivered` is what you want.

**Behaviour worth remembering:** only the DRK email can fail a submission. A
bounced receipt or a Telegram outage returns `200` with a `warnings` array,
because the submission is already safe and making someone refill seven screens
over a failed courtesy email is the worse outcome.
